# TraceGrid production readiness

**Conditionally ready to prepare controlled staging.** Hosting must fit a zero-cost budget. Public launch depends on proving the hosted TLS, WebSocket, database and egress configuration, confirming approved SMTP delivery, and exercising backups under the planned operator identities. Screen-reader sign-off remains open.

## Free-hosting requirements

Provider selection is pending. Oracle Cloud Always Free is a candidate for a persistent VM. Verify eligibility for the actual account and home region, available VM shape and capacity, CPU and memory headroom for the app and PostgreSQL, and compatibility with the installed Python and frontend dependencies. Review Oracle's usage restrictions and idle-instance reclamation policy. A VM running a lightweight 30-second scheduler can still qualify as idle. [Oracle Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm), [Oracle Free Tier FAQ](https://www.oracle.com/cloud/free/faq/)

- Verify that compute, persistent PostgreSQL storage, encrypted off-host backup storage, public networking, HTTPS and expected traffic all fit within the ongoing free allowances. Check billing behavior when quotas are hit and after any trial expires. Exclude configurations that rely on expiring credits or incur overage charges. Verify applicable usage restrictions for outbound monitoring and relay traffic.
- Require an API process that can run continuously without sleeping or scaling to zero, with support for background scheduler and incident email workers. Keep the 30-second monitoring interval and authenticated WebSockets. Verify WSS upgrades, idle connections beyond one heartbeat, reconnect and live updates through the actual ingress. In later restricted staging, use a synthetic endpoint and observe consecutive scheduled slots through an idle period and restart. Treat polling fallback as recovery during a disconnect.
- Plan for separate HTTPS frontend and API hostnames and one authoritative private PostgreSQL database. If no free candidate meets the checks, continue with local staging and defer hosted staging.

## Configuration and security

- Build the frontend using Node 24, `npm ci` and `npm run build`. Set `VITE_API_BASE_URL` to the public HTTPS API origin before building. Treat every `VITE_*` value as public. Serve `dist` with an SPA fallback for direct visits to account and workspace routes. Cache hashed static assets and revalidate the page shell.
- On a self-managed VM, use Python 3.12 and `python -m app.serve --host 127.0.0.1 --port 8000 --workers 1` behind a local reverse proxy. On managed hosting, bind to the platform's required address and port behind its ingress. Keep reload disabled. Serve the API only through ingress, publish HTTPS/WSS, and preserve WebSocket upgrades at `/ws/monitoring`. Allow idle streams beyond the 30-second heartbeat and verify reconnect on restart. [Caddy reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)
- Set `FRONTEND_ORIGINS` to a JSON list of exact HTTPS origins and `TRUSTED_PROXY_NETWORKS` to the actual ingress peer networks only. A same-host proxy can use `127.0.0.1/32` if it is the only reachable peer. Have ingress overwrite forwarded scheme and source headers. Confirm client attribution with controlled requests and enable HSTS after validating HTTPS. Apply ingress body, connection and handshake limits in addition to the app's limits.
- Inject `DATABASE_URL`, `SECRET_KEY` and any SMTP credentials through the service manager or platform secret store. Use a high-entropy signing key shared by all workers. Rotate keys as a coordinated restart and expect existing sessions to end. The browser uses bearer JWTs in local storage and sends WebSocket authentication in its first message. Serve the frontend from a dedicated origin, keep scripts first-party and test a Content Security Policy that allows only the needed API and WSS connections.
- Keep PostgreSQL private. Use a session-capable direct or session-pooled connection for `LISTEN` and advisory locks. For a remote database, verify TLS identity with the provider CA. Separate runtime DML, migration ownership, read-only backup and deployment permissions. Include the application deletes already required for user-initiated endpoint removal and worker housekeeping. Leave monitoring-history retention disabled in the application service.
- Deny probe traffic to private networks, loopback, link-local and platform metadata at the network boundary. Allow the application only the explicit database, resolver and mail routes it needs, alongside permitted public HTTP(S) probe destinations. Start the pilot with ordinary public HTTP(S) ports and document any restrictions on custom ports. Preserve validated-IP pinning, TLS hostname verification, no redirect following and the 10-second probe deadline. A provider's accepted policy and controlled egress checks are release gates.

Recommend an active ruleset targeting `refs/heads/main` with required pull requests, one independent approval, stale approval dismissal, approval of the latest reviewable push by another reviewer, resolved conversations, and up-to-date required checks. ## Before public rollout

1. Verify the free-hosting gates, then seek approval for provider selection and any later provisioning. Review GitHub rules separately and run all three CI checks for the release candidate.
2. Prepare a restricted staging environment. Confirm TLS, WSS, proxy trust, database permissions, egress policy, health alerts and restart behavior using synthetic data.
3. Obtain approval for the controlled relay and owned probe tests. Complete human screen-reader sign-off.
4. Schedule encrypted off-host backups. Practice recovery from an off-host copy and agree on recovery time and data-loss limits. For a live migration, obtain explicit approval after the fresh backup, isolated restore and rehearsal in the [recovery runbook](recovery.md).
5. Open public traffic only after those checks pass and an operator accepts the rollout and rollback plan.
